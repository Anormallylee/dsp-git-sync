# Git transport implementation plan

Goal: retain the Steam-native entry point and safe save/blueprint/mod handoff, replacing complete/change ZIP transport with Git object deltas.
Architecture: separate private data repository checkout (never the live game directory), a complete SHA-256 manifest committed with files, local baseline state, and the existing native Windows Steam wrapper / macOS worker bridge. Git commit IDs become revision IDs. No auto-merging binary saves, no force pushing, no credentials in config URLs, and no public game data.
Stack: Python standard library, Git CLI, Windows C wrapper, launchd on macOS.

1. Isolate existing inventory, validation, three-way merge, file transaction and rollback primitives. Preserve original test coverage and add repository transport integration tests using real temporary bare Git remotes.
2. Implement Git initialization, fetch/ancestry checks, safe tree validation (no symlinks, submodules or executable hooks from data), manifest verification, staged receive, commit and non-force push with retry recovery after uncertain push completion. Local checkout must be disposable; remote commit and baseline are authoritative.
3. Bind Steam lifecycle to new transport and separate git state directory. Retain interrupted-session guards. Failed sync blocks launch; quit publishes changed files and records confirmed remote commit. Authentication remains in OS/Git helpers. Installers preserve machine paths and back up prior tooling.
4. Verify round trips, Chinese paths, deletions, save/mod conflicts, independent blueprints, interrupted push and external writers. Review before deployment.
5. Migrate from existing backend only after confirming current remote and reconciling local additions against its verified baseline. Never choose latest by timestamps alone. Preserve old backend and data for rollback. Test production migration separately from automated Steam launch validation.
6. Ship source and Windows upgrade documentation; run platform-neutral tests in CI. Real Windows play/exit verification remains a separate required handoff step.

Public repository contains only code, synthetic fixtures and generic configuration examples. Operational locations, hostnames, copied saves, service backups and authentication material stay outside it.
